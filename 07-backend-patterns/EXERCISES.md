## 限流（rate_limiter）

**1.1〔预测〕** `limiter := rate.NewLimiter(rate.Limit(2), 1)`（每秒 2 个令牌、桶容量 1）。5 个 goroutine **同时**调用 `Allow()`，几个返回 true？如果换成 `Wait(ctx)` 且 ctx 超时 500ms，行为有什么不同？

**1.2〔改造〕** `rate_limiter` 的 HTTP 中间件是全局限流。改成**按 API Key 限流**：每个 key 独立的 limiter（10 QPS、burst 5），不存在的 key 动态创建，并防止 map 并发写坏。

**1.3〔徒手〕** 不用 `golang.org/x/time/rate`，用"带缓冲 channel + 定时补充"实现一个简化版令牌桶：容量 N，每秒补充 N 个令牌。能说清楚它和 `x/time/rate`（惰性计算）的实现差异加分。

**2.3〔思考〕** `singleflight` 版本里，如果那个"唯一的 DB 查询"返回了 error，50 个并发请求会发生什么？这是好事还是坏事？如果 error 是"数据库挂了"，怎么避免 50 个请求之后又是 50 个请求把 DB 打死（提示：error 也要有短 TTL 缓存 / 熔断）？

## 分布式锁（distributed_lock）

**3.1〔思考〕** 锁 TTL 5 秒，但持锁的业务执行了 8 秒——第 5~8 秒发生了什么？redsync 的 `Extend`（续期/watchdog）解决什么问题？Java 的 Redisson 是怎么自动做这件事的？

**3.2〔找 bug〕** 客户端 A 拿锁（TTL 5s），业务卡了 6 秒，锁自动过期，客户端 B 拿到锁。第 6 秒 A 恢复，执行 `DEL lockkey`——发生什么？标准修复（随机 token + Lua 比对删除）为什么必须是 Lua？

**3.3〔思考〕** Redis 主从架构下，master 写入锁后还没同步到 slave 就宕机、slave 升主——锁丢了，两个客户端同时持锁。这个场景说明"Redis 分布式锁"的什么本质局限？RedLock 是什么、为什么它有争议？如果你要"较强正确性"，实际会选什么存储？
